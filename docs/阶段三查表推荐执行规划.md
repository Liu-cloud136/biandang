## 一、目标与验收口径

### 1.1 一句话目标

`getRecommendation` 的 main 链路从「hy3 实时现编 JSON」切换为「内存热层候选池 → 算法打分排序 → 冷表批量取数 → 库内完整句拼装」，**关键路径零 AI 调用、零 hy3 额度消耗**；live（AI）分支完整保留为秒切回退，不做删除。

### 1.2 量化验收

| 指标 | live 现状（基线） | lookup 目标 | 测法 |
| --- | --- | --- | --- |
| 出文耗时（main，单场景） | ≈18s（hy3 物理下限 13~19s，见延迟调研 §0） | **P95 ≤ 1.5s** | 云函数日志耗时字段，切量后抽 1000 次统计 |
| hy3 额度消耗（main 链路） | 每次出文 ≈2~3 次 hy3 调用（main + 探索 + 偶发 regen/calibrate） | **0** | 上游调用日志 / aiGateway label 计数 |
| 出文成功率 | 受上游 429/超时影响（UPSTREAM/BUSY 分档） | **≥ 99.5%**（无上游依赖，仅 DB） | errType 分档日志统计 |
| 文本内容安全 | AI 实时文本过 msgSecCheck（449 拦截） | **运行时免检**（文本全部来自已审核入库库，安全纪律在入库端闭环） | 抽查返回文本均出自 dish_recommend |
| 多样性：同用户 7 天菜名重复率 | live 影子期实测基线 | **不劣于 live 基线 +3pp** | 影子双算运行**满 7 个自然日完整窗口**后对比（口径见决策 9/D9） |
| 采纳率 | live 基线 | **≥ live 相对值 95%**（灰度 10% 期对比） | commitRecommendation 采纳统计 |
| 探索位 | 按概率 AI 现编 1 道（exploreProb 0.05~0.85） | exploreProb 机制原样沿用（0.05~0.85 自学习），命中时 UCB 定向从库抽低曝光菜，**零 AI** | 日志 explore 来源标记 |

### 1.3 范围声明（做什么 / 不做什么）

- ✅ 一期：main 出文查表化（候选生成、排序、探索位、理由文案、营养取数）。
- ✅ 一期：`recommend_mode` 开关 + 影子模式 + 灰度机制（基建先行，门槛达标前不切量）。
- ✅ 一期：修复 `dish_lexicon` 全量读取 `limit(1000)` 截断（分表方案 B.2#6 遗留 bug，lookup 的前置条件）。
- ⏸ 二期（另立规划）：weekplan（一周规划）查表化——本质是批量选菜，查表天然适配，但涉及跨天多样性编排，一期验证多样性指标后再动。
- ❌ 不动：fridgeCook（冰箱剩菜组合推理）、trySomething、leftover（剩菜改造）保留 AI 现编——三者需要围绕用户输入做生成式推理，查表无法覆盖，属「维护期 AI」合理驻留（对应演进路线「env2/AI 只在需要时维护」）。

## 三、现状基线（2026-08-29 代码核查）

> 以下全部为实读 `cloudfunctions/getRecommendation/index.js`（7000 行，BUILD_TAG=`2026-08-27.env1-hy3-preview-removed`）的结论，供实施者对照，行号以当前工作区为准。

### 3.1 main 主链路现况（AI 在哪里）

```
鉴权/限流（TXT_SLOT_N=10 分布式信号量，index.js:92）
→ 场景上下文：偏好/近窗历史/黑名单/天气/节气/persona（全查表）
→ buildTextPrompt（index.js:2110）：把权重清单+漂移+探索方向+营养软段拼成巨 prompt
→ genTextWithFallback（label:'main'，index.js:5500）：hy3 单通道生成 JSON
   {groups:[{scene, dishes:[{name,cuisine,reason(4字)}], staples:[…]}]}
→ parseRecommendations（index.js:3790）：语义归类校验 + dishCap=3 防御截断（最终恒 2 道/场景）
→ normItem（index.js:3632）：capReason4 压成恰好 4 字 + estimateNutrition 营养补全
→ ensureNutri/mergeGroups（index.js:5558）：营养已走 dish_nutrition_v2 查表优先，未命中 fire-and-forget AI 估算写回
→ 独立探索小调用 exploreSceneCall（index.js:5513）：exploreProb 概率触发，hy3 现编 1 道探索菜，
   成功则替换主出文第 2 道【置顶】，并写 dish_lexicon_pending
→ mmrRerank/dedupCrossScene（index.js:1599+）：主蛋白质 MMR + 跨场景去重
→ 问题场景丢回 AI regenProblemScenes（index.js:6882）：去重后 <2 道时重出（AI）
→ 返回 {recommendations, sceneMode, exploreTarget, exploreCross, city, weatherCtx}（index.js:6231）
```

**结论**：main 链路 AI 调用点共 3 类——①主出文（label:'main'，关键路径）；②探索小调用（label:'explore'，概率触发）；③修复性补生成（regenProblemScenes / calibrate / rename / garnish-reason / reason-fallback / nutri-est，均为失败兜底或质检步）。lookup 分支需同时消灭 ①②，并结构性消灭 ③（库内数据天然合规，无「AI 偶发怪名/缺菜」问题）。

## 四、总体设计

### 4.1 双模式架构与开关

```
sys_config · _id:'recommend_mode'
{
  mode: 'live' | 'lookup' | 'shadow',   // shadow = 双算双记，只返回 live 结果；lookup 侧全链路只读（副作用写内存假想表，D5）
  ratio: 0~100,                          // 按 openid 哈希灰度百分比，mode='lookup' 时生效
  allowOpenids: [ … ],                   // 管理员白名单先行体验，不受 ratio 限制
  autoFallback: true                     // lookup 链路异常时本次请求自动降级 live
  autoCircuit: true                       // D11 全自动熔断：成功率<99.5% 或降级率>2% 连续 1h 自动切回 shadow
}
```

- 读取时机：main 入口读一次（对齐 thompson_switch 读法 index.js:5339），缺失/解析失败 → 默认 `{mode:'live'}`，**默认行为与现状完全一致**。
- 管理入口：复用 manageCFSwitch 或 adminGeneric 通用写 sys_config，不新建管理函数；管理后台加一个开关卡片（mode/ratio/白名单/闸门达成率展示）。
- 切量阶梯：shadow（默认）→ 白名单 lookup → ratio 10% → 50% → 100%。每级观察 ≥3 天，指标见 §1.2。⚠️ **D12（当前无真实流量）**：白名单 → 100% 走快通道（自测 1~2 天即可全量），10%/50% 档保留为有真实流量后的观察档位。
- **自动降级**：lookup 分支任何异常（DB 超时/候选池不足/取数失败）→ 本次请求原地转 live 链路返回，记 `[lookup-fallback]` 单行日志 + 内存计数（供管理后台展示降级率）。降级率 >2% 连续 1 小时应在管理后台标红。
- **全自动熔断（D11）**：窗口级健康监控——「成功率 <99.5%」或「降级率 >2%」任一连续 1 小时 → 自动将 `recommend_mode` 写回 shadow（sys_config 自动写，走 manageCFSwitch 同机制，用户已拍板放开此项边界），记 `[lookup-circuitbreak]` 单行日志；恢复需人工复核后手动提级。

### 4.2 lookup 链路五步（替换 index.js:5492~5558 的 AI 段）

```
① 热层候选池（模块级内存缓存，TTL 60s，无锁单飞刷新）
   dish_lexicon where valid:true（E2 修复后无截断）
   ⨯ left join dish_profile（_id=norm_id）
   → hotPool = [{norm_id, name, kind, category, cuisine, mealTime, source, createdAt, profile}]
   规模 2500~5000 条 × <1KB ≈ 内存 2~5MB，云函数可承受；冷启动首次请求付一次全量拉取（~300ms），
   后续命中零 DB 往返。warmup action（index.js:4753）顺带预热。

② 硬过滤（内存，微秒级）
   忌口/过敏原（user_no_map + prefs.avoid，词汇匹配 name+profile.main+profile.flavors）
   黑名单：管理拉黑（blockedDish）、怪名黑名单（RUNTIME_BLOCKED）、用户差评菜——live 靠 prompt 软约束，
   lookup 是硬过滤，此处遗漏会直接推出黑名单菜，属正确性必查项
   近窗去重（recentNames/chosenNames 7 天，口径与 prompt 现状一致）
   场景语义：kind 映射（dishes←kind='dish'；staples←kind='staple'；
   小吃/下午茶场景 staples←kind='drink'，对齐 DRINK_SCENES 现状 index.js:5678）
   餐次过滤：profile.mealTime 含当前场景（早餐/正餐），缺 mealTime 的菜不排除（只降 1 分，容忍维度缺失）

③ 打分排序（内存，沿用现有权重底座 + 两项新加成）
   score = 权重底座分（sync_weights 档位分 × bayesShrink × 时间衰减）
         + aiMatchBonus(profile, prefs)          // E5 新增，公式见 §4.4
         + exploreBonus(dish)                    // E5 新增，新菜探索加成
         − 曝光降权（dish_exposure cnt，沿用现状）
         − 高曝光零采纳降权（cnt≥5 且 accept/cnt<10% 时 −4，替代 env2 文档的 aiRejected 标记，
            动态计算不落新字段，对全部 source 一视同仁）
   每场景取打分前 K=40 进「抽样池」，池内加权随机抽 2 道——避免同分菜每次固定同序，
   这是查表模式多样性的第一道护栏。

④ 探索位（查表化，零 AI）
   exploreProb 命中时：UCB 选方向（沿用 ucbPick/thompsonPick 与 EXPLORE::* 臂统计）
   → 从 hotPool 筛「主食材/名称命中方向词 且 曝光 <3 且 入库 ≤30 天 且 未进该场景打分 top40」的低曝光菜（D10：只推被常规排序埋没的新菜，常规能推的不占探索位）
   → 命中候选不足 1 道则放弃本次探索位（不硬凑）
   → 探索菜参与场景内 MMR 后【置顶替换】主出文第 2 道（对齐现状 index.js:5569 的替换置顶逻辑）
   → bumpExplorePush 方向计数 + dish_exposure 计数沿用；不再写 dish_lexicon_pending（菜已在库）。
     ⚠️ 上述写操作在 shadow 期一律只写内存假想表，E12 灰度真正出文后才写库（决策 5/D5，防污染 live 曝光数据）
   exploreProb 机制原样沿用：查表下探索位虽零成本，仍维持概率触发，防探索占比失控稀释偏好命中；调参观察期后再议

⑤ 冷表取数 + 拼装（每场景 2~3 次 _.in() 批量读）
   top N（2 道 + 2 主食）→ dish_recommend.reason（完整句）/ dish_nutrition_v2.nutrition /
   dish_image_v2.imageUrl 一次取齐（norm_id 主键 _.in）
   → 缺 reason：按 category 从通用评语池确定性抽取（沿用 FALLBACK_REASONS 模式），history 源菜无 category 时落全局通用池，
     同时记 [lookup-reason-miss] 日志供补齐
   → 缺 nutrition：走 estimateNutrition 本地代码表兜底（现状第三级，零 AI）
   → 缺 image：imageUrl 返回空，前端退 430 占位图 / getDishImage 实时生图（现状兜底不变）
   → cuisine 过 normalizeCuisine 归一；输出结构与 live 完全一致
     （{recommendations, sceneMode, exploreTarget, exploreCross, city, weatherCtx}），前端结构零改动
```

性能预算：热层命中（常态）0 次 DB 往返 + 冷表 2~3 次批量读 ≈ 300~600ms；冷启动 +300ms。**P95 ≤ 1.5s 可达**（对比 live ≈18s）。

### 4.3 开关与分支关系

- 新增顶层 `buildSceneRecsLookup(ctx)` 与现有 `genTextForScenes` 并列，main 入口按 `recommend_mode` 三态分发；**live 路径代码不动**（对照分表方案阶段 4 的「主链路不碰」纪律）。
- regenProblemScenes / calibrate / rename / garnish-reason 等 AI 修复步：live 分支原样保留；lookup 分支天然跳过（无 AI 生成即无 AI 质检），但「场景候选不足」的兜底改为：候选池 <2 道时**自动降级 live**（autoFallback），不做程序硬塞（延续「无程序硬兜底」原则 index.js:5646）。
- TXT_SLOT_N 信号量：lookup 分支不经 AI，**跳过信号量排队、不占用 10 并发槽**（仅条件放行，live 路径不动）——避免高峰期 lookup 用户被 live 形态限流误伤（技术补充 3，§10.2）。
- 与流式改造（stream_v2 / getRecSSE 场景级 SSE）的关系：lookup 出文 ≤1.5s，逐场景推送无增益——**lookup 分支忽略 stream_v2**，始终 callFunction 一次返回；stream_v2（现状未启用）属 live 专用体感增强，未来启用时须与双模式正交组合验证。
- msgSecCheck：lookup 返回文本全部出自已审核入库的 dish_recommend（入库端已过审），运行时免检；live 分支 449 拦截逻辑不动。此差异写入部署说明，避免后续审计困惑。

### 4.4 打分公式细则（E5）

`aiMatchBonus`（对齐《env2补充env1菜谱库.md》§3.4，量纲并入权重底座 0~100 分制，故系数 ×5）：

| --- | --- | --- |
| 口味 flavors ∩ prefs 口味档 | +10 | 每命中一档取最高，不叠加 |
| 菜系 cuisine ∈ prefs.cuisine 强/中档 | +15 / +8 | 档位阈值沿用 w≥85 强 / ≥60 中 |
| 分类 type / category ∈ prefs.veg 类目 | +10 | |
| 忌口命中（任何维度） | **−30 并直接在②硬过滤剔除** | 双保险：过滤为主，打分为漏网兜底 |
| 主食偏好 kind='staple' ∈ prefs.type | +10 | |
| 辣度 profile.spicy 与 prefs 辣度档落位 | ±5~10 | 偏好重辣+高辣菜加分，偏好清淡+高辣菜重罚 |
| 时令调权（确定性节气/气温规则） | ±4~8 | 冬季（12~2 月）凉菜/冷食 −6、汤羹 +4；气温 ≥30℃ 凉饮/凉菜 +5；规则表为代码常量，换季随版本更新 |

weatherCtx（和风天气/节气）在 live 是 prompt 软引导，在 lookup 的消费点即上表时令调权。lookup 分支**照常调和风天气**（非 AI 的外部 HTTP 查询，决策 7/D7），天气数据只进时令调权、不进 prompt——查表模式不丢天气上下文，代价是 lookup 保留一个非 AI 的外部查询依赖（金额与额度均不涉及 hy3）。

`exploreBonus`：`createdAt` 距今 ≤30 天 且 dish_exposure 曝光 <3 → **+8**（量纲对齐「探索分不应盖过强偏好」，低于菜系强档 15）；过期自动失效，无需标记字段。

参数定标方式：P2 影子期对「live 出文菜」反算这两项分的分布，验证 bonus 不主导排序（占比 ≤25%）；超标则整体减半重跑。**禁止拍脑袋上线**。
