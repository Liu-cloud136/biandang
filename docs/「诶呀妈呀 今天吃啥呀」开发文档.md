## 四、核心功能设计

### 4.1 用户完整流程

```
首次打开小程序
    ↓
【首次引导】设置你的饮食偏好
    ├── 口味偏好（多选）：麻辣 / 清淡 / 酸甜（偏酸·偏甜）/ 咸香 / 鲜
    ├── 辣度：不限制 / 微辣 / 中辣 / 重辣
    ├── 菜系偏好（多选）：川菜 / 粤菜 / 日料 / 西餐 / 东南亚 / 江浙菜 / 家常
    ├── 肉类偏好（多级）：家畜(猪肉/牛肉/羊肉/兔肉/驴肉) · 禽(鸡肉/鸭肉/鹅/鸽肉/鹌鹑) · 特色禽类(三黄鸡/乌鸡/老鸭/仔鹅/乳鸽) · 水产(牛蛙/田鸡/黄鳝/甲鱼/泥鳅/淡水鱼/海鲜) · 蛋(鸡蛋/鸽子蛋/鹌鹑蛋)（可细化到小类如里脊肉）
    ├── 青菜偏好（多级）：青菜 / 各类绿叶菜
    ├── 菜类偏好（多级）：如根茎 / 菌菇 / 豆制品…
    ├── 忌口（多选）：不吃辣 / 不吃海鲜 / 不吃猪肉 / 素食 / 过敏原
    ├── 过敏原（多选）
    ├── 用餐场景（多选）：早餐 / 午餐 / 晚餐 / 夜宵 / 下午茶 / 小吃
    └── 配饮偏好：清茶 / 果汁 / 水 / 其它（如豆浆、酸梅汤）
    ↓
保存到云数据库（用户ID关联）
    ↓
进入首页 → 点击「帮我决定」
    ↓
云函数调用混元AI：
    ① 文生文 → 按每个用餐场景分别生成「菜品」(2道) + 「主食」(1~2个)
       每道含：菜系 cuisine、一句话理由 reason、热量/蛋白/碳水/脂肪
    ② 文生图 → 为各项生成写实风配图（并发+持久化到云存储）
    ↓
展示推荐结果页（多场景分组，每项含配图+菜系标签+理由+营养）
    ↓
用户操作：
    ├── 「就它了」→ 记录 selected（所选菜+主食）回流偏好，返回首页
    ├── 「换一批」→ 重新调用，按场景数扣免费额度（或看广告）
    ├── 「看做法」→ 生成该菜食材/步骤/AI点评弹层
    └── 「分享」→ 生成转发卡片（前端 canvas 拼所选菜品缩略图宫格作封面，不走云函数）
    ↓
【看广告获取更多次数】
    ↓
【累积数据，越用越懂你（selected 回流后续推荐）】
```

### 4.3 文生图风格规范

| 风格维度      | 规范                                                                                              |
| --------- | ----------------------------------------------------------------------------------------------- |
| **画风**    | 写实摄影（高清美食照片，非插画/简笔画）                                                                           |
| **色调**    | 自然光、色彩诱人，突出食物质感                                                                                 |
| **构图**    | 浅景深特写，居中突出菜品主体                                                                                  |
| **背景**    | 干净简约背景，不抢主体                                                                                     |
| **风格关键词** | `realistic food photography, natural light, shallow depth of field, clean background, appetizing, professional` |

### 4.5 词表与分类（HIER）

推荐系统的「偏好 → 菜名标签」匹配依赖一份两级联动词表（大类 ⊃ 小类）。选了「大类」又选其中「小类」，视为更偏重小类，推荐时侧重该小类。

词表三处必须严格同步（键名、小类词形完全一致）：
- `cloudfunctions/getRecommendation/index.js` 的 `HIERARCHY`
- `utils/config.js` 的 `HIER`
- `pages/setup/setup.js` 的 `meat`（选项）/ `avoid`（不吃××）/ `WHITE`（过敏原白名单）

菜名池 `dishes.json` 的 `tags.meat` 用大类键名打标；`cookbook.json`（菜谱）+ 镜像 `cookbook_ref.json`（食材数组，供软匹配）+ `pairing_rules.json`（`scripts/gen_pairing.js` 重跑生成）同步维护。

#### 维护约定
- 新增肉类：在 `HIERARCHY.meat`、`HIER.meat` 加大类+小类；`setup.js` 的 `meat`/`avoid`/`WHITE` 三处同步加项；有对应菜则入 `dishes.json` 池并打 `tags.meat`，无则补 `cookbook.json` 菜谱（同步 `cookbook_ref.json`）。最后重跑 `scripts/gen_pairing.js` 并部署 `getCookGuide`、`getRecommendation`。

### 6.2 env2 跨账号 AI 代理（溢出 / 加速）

> 跨账号借用 `wx1111111111111111`（环境 `your-env-id-2`）的混元额度与独立并发，缓解 env1 上游并发雪崩；跨账号调用统一经 `aiProxy` 云函数转发。
>
> **后台可实时调整（2026-07-22 新增）**：env2 的开关、模式、分流比例不再写死在部署环境变量里，改为运行时读取 `sys_config.env2` 集合（60s 内存缓存），由 `manageEnv2` 云函数读写。管理员后台新增「env2 配置」模块（第 ⑧ 项），可一键切换 `overflow`/`accelerate`、调节 `ENV2_SPLIT`，**无需改代码或重新部署云函数**即生效。

**线上配置（verified 2026-07-21，由 CloudBase MCP 拉取）**：

| 函数 | ENV2_ENABLED | ENV2_MODE | ENV2_SPLIT |
| ---- | ---- | ---- | ---- |
| `getDishImage`（生图） | `true` ✅ | `overflow` | `50` |
| `getRecommendation`（出文） | `true` ✅ | `overflow` | `50` |
| `validateAllergen`（过敏原校验） | 代码已支持 env2 兜底，环境变量未单独核实 | — | — |

**两种工作模式**：

| 模式 | 触发方式 | 适用场景 |
| ---- | ---- | ---- |
| `overflow`（默认） | 仅当 env1 本地信号量打满（`SlotBusyError`：出图 2 槽 `img_slot_0/1`、出文 5 槽 `txt_slot` 全占满）时，才把请求溢出到 env2 借额度 | 平时流量不高的常态 |
| `accelerate` | 平时即按 `ENV2_SPLIT` 比例（如 `50`）把请求**提前**分流到 env2，抬升总并发天花板 = env1 槽位 + env2 份额 | env1 信号量已成为瓶颈的高并发场景 |

**性能取舍（选型依据）**：
- **低流量 / 平时**：`overflow` 反而更快——请求全走本地 env1，无跨账号一跳；`accelerate` 会强行把约一半请求绕去 env2（多一次网络 hop），env1 闲着却白白增加延迟，且持续消耗 env2 额度（即便 env1 很闲）。
- **高并发**：`accelerate` 更快——提前双车道并行，省去"先撞 env1 墙、抢不到槽才溢出"的排队 + 异常开销。

**何时该切 `accelerate`**：云函数日志里**频繁**出现 `[env2] 出图溢出成功` / `[env2] 文本溢出成功` / `[garnish][reason][env2] 文本通道繁忙，借 env2 重写理由` 等字样 → 说明 env1 经常被打满 → 此时在管理员后台「env2 配置」把 `ENV2_MODE` 改为 `accelerate`（**后台一键切换，无需改代码/重新部署**）才划算。

**实测（2026-07-21，最近一天）**：`getRecommendation` 仅 6 次调用、`getDishImage` 19 次调用，全部 `RetCode=0`，抽样日志无任一条 `[env2]` 溢出记录 → **env1 当前未打满，保持 `overflow` 即可，暂不必切 `accelerate`**。

> 注：代码无"按单次请求强制走 env2"的开关——`routeEnv2First()` 在 `overflow` 下恒返回 `false`；若需"仅某次请求走 env2、其余不变"，须改代码加请求级标志（如入参 `forceEnv2`）后重新部署。

### 6.3 getRecommendation 核心逻辑（仅出文，不扣次）

> **职责边界（2026-08-14 重构）**：`getRecommendation` 现在**只负责出文**（文生文 + 探索方向抽取 + 黑名单过滤 + 内容安全），**不再扣次、不再入库**。扣次、历史入库、探索采纳回写统一收敛到 `commitRecommendation`（用户点「就它了」/「换一批」提交选择时调用），详见 6.3.1。这样拆分让"先看结果、再决定扣不扣"更可控，也避免出文即扣次但用户未采纳的浪费。

```javascript
// 云函数：getRecommendation（真实实现摘要）

const tcb = require('@cloudbase/node-sdk');
const app = tcb.init({ env: 'your-env-id-1' });
const ai = app.ai();
const TEXT_MODEL = 'hy3';                                   // 混元文本模型
// 文生图已拆分为独立云函数 getDishImage（单道菜出图 + 持久化，不扣次），本函数只出纯文本，每菜 imageUrl='' 初始化

// 运行时缓存：怪名黑名单（每次调用实时读取，无本地缓存）
let RUNTIME_BLOCKED = [];        // type≠ingredient：整串坏样本（候选过滤 + 重命名提示）
let RUNTIME_INGREDIENTS = [];   // type==='ingredient'：单字小料（香菜/葱/蒜…，用于剥后缀 & 蒜香 前缀）
let RUNTIME_BLOCKED_ALL = [];    // 全部 term：仅用于重命名提示词

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext();
  if (!OPENID) return { code: 401, msg: '未获取到用户身份' };

  // 1. 读取偏好（服务端直读，绕过 doc 级权限）
  const prefsRes = await db.collection('user_preferences').where({ _openid: OPENID }).limit(1).get();
  const prefs = prefsRes.data[0];
  if (!prefs) return { code: 400, msg: '请先设置饮食偏好' };

  // 1.1 拉取最近推荐菜名（避免重复）+ 用户真正选中的菜名（偏好回流）
  let recentNames = [], chosenNames = [];
  const histRes = await db.collection('recommend_history')
    .where({ _openid: OPENID }).orderBy('timestamp', 'desc').limit(10).get();
  histRes.data.forEach(h => {
    (h.recommendations || []).forEach(g => {
      (g.dishes || []).concat(g.staples || []).forEach(it => { if (it?.name) recentNames.push(it.name); });
    });
    (h.selected || []).forEach(s => { if (s.name) chosenNames.push(s.name); if (s.staple) chosenNames.push(s.staple); });
  });

  // 2. ⚠️ 不在此扣次、不在此写历史：出文阶段只生成候选，次数校验/扣减/入库统一在 commitRecommendation（见 6.3.1）
  //    本函数仅负责生成并无副作用返回，前端点「就它了/换一批」再调 commitRecommendation 提交选择

  // 2.0 拉取怪名黑名单（分页全量读取，无 100 上限；按 type 拆分缓存）
  RUNTIME_BLOCKED = []; RUNTIME_INGREDIENTS = []; RUNTIME_BLOCKED_ALL = [];
  let skip = 0;
  while (true) {
    const bl = await db.collection('name_blocklist').skip(skip).limit(100).get();
    (bl.data || []).forEach(d => {
      const t = (d.term || '').toString().trim();
      if (!t) return;
      RUNTIME_BLOCKED_ALL.push(t);
      if (d.type === 'ingredient') RUNTIME_INGREDIENTS.push(t);
      else RUNTIME_BLOCKED.push(t);
    });
    if (!bl.data || bl.data.length < 100) break;
    skip += 100;
  }

  // 3. 文生文（按场景切片并发，每片 2 个场景）
  const model = ai.createModel('cloudbase');
  const chunks = chunk(prefs.scene || ['正餐'], 2);
  const groupsArr = await Promise.all(chunks.map(scenes =>
    model.generateText({ model: TEXT_MODEL, messages: [{ role: 'user', content: buildTextPrompt(prefs, recentNames, chosenNames, scenes) }], temperature: 0.9, topP: 0.9 })
      .then(r => parseRecommendations(r.text))
  ));
  const recommendations = groupsArr.flat();
  if (!recommendations.length) {
    // 非异常但结果为空：归 UPSTREAM，便于与代码缺陷(BUG)区分
    console.error('[getRecommendation][UPSTREAM] 推荐结果为空 scene=' + (event && event.scene || '-'));
    return { code: 500, errType: 'UPSTREAM', msg: '推荐生成失败，请稍后重试' };
  }

  // 4. 初始化图片占位（真实出图已拆分到 getDishImage，由前端并发调用，图到即回填 imageUrl）
  recommendations.forEach(g => {
    (g.dishes || []).concat(g.staples || []).forEach(it => { it.imageUrl = ''; });
  });

  // 5. ⚠️ 不写历史、不扣次：返回本次生成的候选给前端；历史与扣次由 commitRecommendation 在用户提交选择时处理

  // 6. 返回（内容安全校验在步骤 3.5 已做，命中违规直接返回 449）
  return { code: 200, data: { recommendations, exploreDirs, exploreCross } };
};
```

要点：
- **菜品 / 主食分离**：`dishes`（每场景 2 道）+ `staples`（1~2 个主食 / 小吃场景为 1 个配饮），菜名禁止出现主食形态词。
- **菜系字段**：每项输出 `cuisine`（川菜/粤菜/家常…）；小吃配饮额外输出 `cat`（清茶/果汁/水/其它）供前端判定「看做法」。
- **选择回流**：`chosenNames` 由 `recommend_history.selected` 收集，写进提示词，后续偏向同类食材/风味/做法。
- **怪名黑名单（name_blocklist）**：每次调用实时分页读取（无 100 上限），按 `type` 拆分——`example`（整串坏样本，如「蒜香拌韭菜」）用于候选过滤 + 重命名提示词；`ingredient`（单字小料，如 香菜/葱/蒜/姜/辣椒）用于 `stripGarnish` 剥除「菜+小料」后缀及「小料+香」前缀（如「蒜香炒黄瓜」→「炒黄瓜」），**不依赖通顺性校验**，彻底规避怪名。
- **出图拆分（getDishImage）**：文生图独立为单道菜出图函数（不扣次、持久化云存储），前端拿到推荐后并发出图、图到即回填 `imageUrl`；历史记录经 `recordFeedback` 写入带 `imageUrl` 的副本，保证历史页显示图片。
- **场景互斥 / 小吃配饮**：前端拦截「小吃」与「下午茶/夜宵」同时选；「小吃」场景只出地道小吃 + 1 个配饮（清茶/果汁口语化展开，水/豆浆等保持原样）。
- **探索方向抽取**：`getRecommendation` 在出文的同时抽取"探索方向"（`exploreDirs` 单场景探索大类、`exploreCross` 跨场景组合），返回给前端，由 `commitRecommendation` 在用户采纳时精确回写 `dish_exposure`（命中探索大类才 `accept+1`，未命中仅保留出文侧 `cnt`），实现"探索-利用"闭环而不污染历史展示。
- **职责边界（不再扣次 / 不再写历史）**：`getRecommendation` 仅出文并返回候选 + 探索方向；次数校验、阶梯扣次、历史入库、探索采纳回写全部收敛到 `commitRecommendation`（用户点「就它了 / 换一批」提交 `selectedDishes`/`exploreDirs` 时调用）。详见 6.3.1。
- **内容安全**：推荐文本（菜名 + 理由）经 `msgSecCheck` 校验，命中违规(87014)返回 449 拦截；接口异常仅 `console.warn` 放行，不阻断业务。

#### 6.3.1 结构化错误处理与日志（2026-08-06 改造，已部署 env1）

目的：原先所有异常一律 `catch → {code:500, msg:err.message}`，前端 `onDecide` 又把「非 200」统统弹「出文通道繁忙」——代码 bug（`ReferenceError` 等）与真实限流在用户侧、日志侧长得一模一样，每次排障靠猜。**现按异常类型分档，日志带固定前缀便于 CLS 检索，响应带 `errType` 让前端给差异化文案。**

后端新增统一失败出口（位于 `SlotBusyError` 类定义之后）：

```javascript
const ERR_TYPE = { BUG:'BUG', DB:'DB', UPSTREAM:'UPSTREAM', BUSY:'BUSY', UNKNOWN:'UNKNOWN' };
const CODE_BUG_ERRORS = ['ReferenceError','TypeError','SyntaxError','RangeError'];
function classifyError(err) {
  if (!err) return ERR_TYPE.UNKNOWN;
  const name = err.name || '';
  const msg = String(err.message || '');
  if (CODE_BUG_ERRORS.indexOf(name) >= 0) return ERR_TYPE.BUG;       // 重试必然失败
  if (/database|collection|DATABASE_|_ID_|document|permission denied/i.test(msg)) return ERR_TYPE.DB;
  if (/429|timeout|ETIMEDOUT|ECONNRESET|socket hang up|502|503|504|rate ?limit/i.test(msg)) return ERR_TYPE.UPSTREAM;
  return ERR_TYPE.UNKNOWN;
}
function failure(err, ctx) {
  const type = classifyError(err);
  const c = ctx || {};
  const at = String((err && err.stack) || '').split('\n')[1];
  const line = '[getRecommendation][' + type + ']'
    + ' action=' + (c.action || '-') + ' scene=' + (c.scene || '-')
    + ' name=' + ((err && err.name) || '-') + ' msg=' + ((err && err.message) || '-')
    + (at ? ' at=' + at.trim() : '');
  if (type === ERR_TYPE.BUG) console.error(line + '\n' + ((err && err.stack) || ''));  // 附完整堆栈
  else console.error(line);
  return { code: 500, errType: type, msg: USER_MSG[type] || USER_MSG.UNKNOWN };
}
```

要点与约定：

- **`errType` 分档**（两端枚举必须保持一致）：
  - `BUG` — `ReferenceError`/`TypeError`/`SyntaxError`/`RangeError` 等代码缺陷，**重试 100% 失败，必须改代码告警**；
  - `DB` — 集合不存在 / 权限 / 超时；
  - `UPSTREAM` — 429 / timeout / 5xx 等上游异常（退避重试有效）；
  - `BUSY` — 信号量占满（即原 430，正常拥塞）；
  - `UNKNOWN` — 未归类。
- **日志固定单行格式**：`[getRecommendation][<TYPE>] action=.. scene=.. name=.. msg=.. at=<堆栈首行>`。⚠️ 本环境 CLS 只支持对 `log` 字段做纯文本匹配，**严禁改成对象日志**，否则 CLS 搜不到。排障入口：CLS 纯文本搜 `[BUG]` 捞代码缺陷，`[UPSTREAM]`/`[DB]`/`[BUSY]` 分别看上游/库/拥塞。
- **430 改打 `console.warn`**：正常拥塞不再污染 error 日志，避免淹没真实故障。
- **收口点**：main catch、`handleTryActions`、`handleFridgeCook`、`saveFridgePick`(套 `Object.assign` 保留「保存失败」文案)、`handleWeekPlan`、`handleLeftover` 共 6 处，以及「recommendations 为空」非异常分支（显式标 `UPSTREAM`）。
- **前端联动**（`pages/index/index.js`）：顶部新增 `ERR_TOAST` 映射 + `errTypeToast(type,msg)`；`genTextForScene` 在 `errType==='BUG'` 时**立即 break 不再退避重试**（省 3 轮空等），catch 分支标 `NETWORK` 与云端业务错误区分；失败分类留痕到 `recs[gi]._errType/_errMsg`，`onDecide`/`onRetryScene` 据此给差异化文案——只有 `BUSY`/`UPSTREAM` 保留「稍后重试」，`BUG` 改为「服务开小差了，我们已收到反馈」。**前端改动待发版（robocopy → 开发者工具上传）才对用户生效；后端已即时生效。**

### 6.3.2 commitRecommendation（阶梯扣次 + 入库 + 探索回写）

> 2026-08-14 重构后，次数消耗与历史落库的唯一入口。前端在用户点「就它了 / 换一批」时提交 `selectedDishes`（已选菜品/主食）与 `exploreDirs`（探索方向），本函数统一：跨场景去重 → 阶梯扣次 → 写历史 → 精确回写探索采纳。

核心逻辑要点：

- **阶梯扣次**：`DEDUCT = 已选场景数`（每场景 1 点，温和线性）。可用 = `baseFree + bonusFree`，**先扣 `baseFree` 不足再扣 `bonusFree`**；`bonusFree` 不受 `FREE_CAP=50` 上限约束（管理员/兑换码发放的额度可超额累积）。
- **场景互斥兜底**：前端已拦截「小吃」与「下午茶/夜宵」同时选；提交时再按全局合并场景名去重，避免重复扣次。
- **历史入库**：`addHistoryRetry`（带重试）写 `recommend_history`，`selected` 记录用户最终选择，供后续偏好回流（`getRecommendation` 的 `chosenNames`）。
- **探索采纳回写 `dish_exposure`**：仅当用户**命中**某探索大类时 `accept+1`；未命中探索方向的菜仅保留出文侧 `cnt`（展示累计，不影响探索权重），实现"探索-利用"不污染常规推荐。
- **探索进度读取**：`getDailyStats` 汇总 `dish_exposure` 返回"已探索 X / 待探索 Y"，前端「我的」页展示探索进度。

```javascript
// 云函数：commitRecommendation（真实实现摘要）
exports.main = async (event) => {
  const { selectedDishes = [], exploreDirs = [] } = event;
  // 1. 跨场景去重 + 计算 DEDUCT
  const sceneSet = new Set(selectedDishes.map(d => d.scene));
  const DEDUCT = sceneSet.size || 1;
  const prefs = (await db.collection('user_preferences').where({ _openid: OPENID }).limit(1).get()).data[0];
  const baseFree = prefs.baseFree || 0, bonusFree = prefs.bonusFree || 0;
  if (baseFree + bonusFree < DEDUCT) return { code: 403, msg: '免费次数不足' };

  // 2. 阶梯扣次：先 baseFree 后 bonusFree
  const fromBase = Math.min(DEDUCT, baseFree);
  const fromBonus = DEDUCT - fromBase;
  if (fromBase > 0) await db.collection('user_preferences').doc(prefs._id).update({ data: { baseFree: _.inc(-fromBase) } });
  if (fromBonus > 0) await db.collection('user_preferences').doc(prefs._id).update({ data: { bonusFree: _.inc(-fromBonus) } });
  await logFree(OPENID, 'deduct', 'recommend', DEDUCT, '推荐决定 -' + DEDUCT);

  // 3. 写历史（重试）
  await addHistoryRetry({ recommendations, selected: selectedDishes, _openid: OPENID });

  // 4. 精确回写探索采纳（命中探索大类才 accept+1）
  for (const dir of exploreDirs) {
    const rec = await db.collection('dish_exposure').where({ dir }).get();
    if (rec.data.length) await db.collection('dish_exposure').doc(rec.data[0]._id).update({ data: { accept: _.inc(1) } });
  }
  return { code: 200, data: { remaining: baseFree + bonusFree - DEDUCT } };
};
```

### 6.6 社区贡献与反馈审核

#### 社区贡献流程

```
mine 页「贡献菜名或食材」
    ↓
submitContribution（取 userNo → 库去重 → name_blocklist 比对 → AI 审核 ok/fake/dup → 落 dish_contrib）
    ↓
达阈值自动 mergeContributions（菜名满 50 / 食材满 5）
    ↓
merge：valid 贡献 upsert 进 dish_library / ingredient_library（去重）
    + 按 userNo 发放（菜名×2 / 食材×1，写 bonusFree + free_log）
    + 标记 status=merged 防重复发放
```

- **阈值（2026-07-21）**：菜名 `DISH_THRESHOLD=50`、食材 `ING_THRESHOLD=5`（submitContribution 与 mergeContributions 一致）；`DISH_REWARD=2` / `ING_REWARD=1`。
- **强制合并**：后台「立即合并（强制）」走 `mergeContributions.merge(force)`，绕过阈值整批合并所有 valid 记录。
- **单条合并**：贡献审核页每条「合并」按钮走 `manageContrib.mergeOne(id)`→`mergeContributions.mergeOne(id)`，把该条单独入库发次并标记 merged；已 merged 的跳过，避免重复发次。「驳回」= `setStatus: blocked`（不入库、不发次）。
- **公共库不动**：注销 `deleteAccount` 仅清个人 `dish_contrib`，公共库 `dish_library`/`ingredient_library` 保留。

#### 反馈审核口径

- 用户经 `submitDishFeedback` 提交菜名反馈，记录 `userNo`（缺失哨兵 `-1`，`0` 专属管理员）。
- 菜名问题类：进 `name_blocklist`（与 5.1 黑名单读取分流一致）。
- 个人忌口类：写本人 `user_preferences.avoidDishes`（去重 ≤50），供 `getRecommendation` 规避；`userAvoid` 供我的页管理删除。
- 后台 `manageFeedback` 审核「有效」给该用户 `bonusFree`+1（写 free_log），「无效」不发放。

### 8.2 邀请裂变机制（⛔ 已终止，保留设计留档）

> **当前状态（2026-08 实测）**：邀请裂变**已终止**。相关云函数 `invite` 与前端 `pages/invite` 页、邀请码生成/助力发放逻辑已从代码移除，不再发放任何裂变奖励。下方为**历史设计留档**，仅供了解原方案，不代表线上行为。
>
> 终止原因：裂变带来自刷/合规边界风险，且对纯工具类小程序收益有限，故下线，免费次数获取改为「签到 + 领 2 次（测试期直发）+ 管理员赠送 + 兑换码」四路（详见 12.1）。

**原链路（云函数 `invite`，已下线）**：

```
用户进入 /pages/invite/invite
    ↓ action=create
生成（或复用）本人专属邀请码 → 存 invite_codes{ code, inviterOpenid, usedCount }
    ↓ 转发 path: /pages/invite/invite?inviteCode=XXX（或海报小程序码 scene=CODE）
好友打开自动 acceptInvite(code) / 或 mine 页手动输码 → action=accept
    ↓ 校验：码有效 + 非本人 + 该 invitee 未接受过（user_invites 幂等防刷）
邀请人 +1 次（grantOne→baseFree，记 free_log type=invite）
被邀请人 +1 次（grantOne→baseFree，记 free_log type=invite_in）
    ↓ 记 share_records + invite_codes.usedCount+1
返回 { invited:true, msg:'助力成功，你和好友各得 1 次' }
```

**原要点**（仅留档）：
- 邀请码去易混字符（I/O/0/1），`invite_codes` 唯一约束生成；
- `user_invites` 按 `inviteeOpenid` 去重 → 同一人只能助力一次（防自刷/重复领）；
- 自己不能接受自己的码（返回 403）；
- 奖励发放不依赖「完成一次决策」，输码即到账；
- 注销时 `deleteAccount` 清理 `invite_codes` + `user_invites`。

### 8.3 兑换码机制（✅ 已实现，2026-08-11）

> 替代已终止的邀请裂变，成为"可控分发"的主要渠道。管理员通过 `manageRedeem` 生成兑换码（写 `redeem_codes`，含 `enabled/expiresAt/quota/used` 字段），用户在小程序「我的」页 `redeemCode` 输入：

- **校验链**：码存在 → 启用中 → 未过期 → 额度未用尽（`used < quota`）→ 本人未重复兑换（`redeem_log` 按 `openid+code` 幂等防刷）；
- **发放**：一次性发放 `count` 次到 `bonusFree`（**不受 `FREE_CAP=50` 上限约束**，可超额累积）；
- **用途**：活动赠送、内测福利、参赛评审体验等定向分发；不依赖广告/裂变，合规边界清晰。

## 十三、附录：注意事项

### 13.1 类目合规

- 选择 `工具-信息查询`，确保不涉及"深度合成"内容
- AI 推荐结果定义为"信息查询辅助"，而非"AI 问答"
- 服务条款需注明："推荐结果由 AI 生成，仅供参考"（已在首页「使用说明」弹层开头注明）
- 隐私合规：客户端 `app.json` 开启 `__usePrivacyCheck__`，`pages/setup` 在收集偏好前弹隐私授权窗（`wx.requirePrivacyAuthorize`）；用户拒绝也放行，避免卡死
- 内容安全：getRecommendation / getCookGuide / generatePoster 均调用 `cloud.openapi.security.msgSecCheck`（**云调用**）校验 AI 生成文本，命中违规（errCode 87014）返回 449 拦截；接口异常/未开通仅 `console.warn` 放行，不阻断业务。权限靠云函数目录 `config.json` 声明 `permissions.openapi:["security.msgSecCheck"]`，由开发者工具上传时自动登记（**非**公众平台后台开关）。generatePoster 当前前端虽未调用，但其文本安检 + `share_records` 记录（含 `inviterOpenid`）已就绪，调用即生效

### 13.2 成本控制

### 14.2 正式上线前：用户编号重置 + 测试数据清理

> 编号分配已改为 **原子事务**（`getPrefs` 用 `counters` 集合 `_id:'user_no'` 计数器在 `db.startTransaction()` 内自增；已释放编号不复用，单调递增）。当前 `counters.user_no.seq=3`、`user_no_map` 含 2 条测试记录（no=2、no=3）。要让正式用户从 **1** 干净起步，必须**同时清两个来源**，只删其一无效：

| 清理对象 | 操作 | 说明 |
| ---- | ---- | ---- |
| `user_no_map` 集合 | 删掉全部测试记录（那 2 条 no=2 / no=3） | 释放编号，但**不**影响计数器 |
| `counters` 集合中 `_id:'user_no'` 文档 | 删除该文档 | 计数器重置；下次 `getPrefs` 时 `ensureCounter` 发现文档不存在 → 重算 `max(no)`（此时 `user_no_map` 也已空 → `max=0` → 首项用户拿 **1**）|

- **只删 `user_no_map`**：计数器 `seq` 仍在 → 下个用户仍拿 4，不回 1。
- **只删 `counters.user_no`**：`ensureCounter` 重算 `max(no)` 还是 3（map 里仍有两条）→ 下个用户仍 4。
- **两个都删** → 编号从 **1** 起步 ✅。

**顺带清理测试微信的其余数据**（否则它们残留于各集合）：
- 推荐走 `deleteAccount`（正确处理 `fav_contrib`/`fav_count` 回退等），或直接清空以下集合的测试数据：`user_preferences` / `recommend_history` / `free_log` / `favorites` / `share_records` / `feedback` / `cook_viewed` / `fav_contrib` / `fav_count`。（launch 时测试数据本就该丢，`fav_count` 跟着清无妨）
- ⚠️ 清空 `user_no_map` 与 `counters.user_no` **要在删除测试用户数据之后**再做，否则 `ensureCounter` 初始化会重算到残留 max 而上不了 1。
