# 出文延迟优化调研文档

> 整理于 2026-08-16。覆盖 onDecide 出文缓慢问题的全链路诊断、已做优化、探针实测结论、以及免费资源边界。
> 项目：「诶呀妈呀 今天吃啥呀」微信小程序 + CloudBase（env1 `your-env-id-1`，小程序成长计划 inspire_plan 免费通道）。

---

## 0. 问题定义

用户反馈：勾选多场景后"今天吃啥"决策（onDecide）整体偏慢，即使已做进度拆分显示，仍觉卡。

实测前端分段耗时结构（单场景）：
- 出文（getRecommendation 主出文）≈ 18s
- 出图（genImagesForGroup）≈ 8s（优化前约 30s）
- commit（commitRecommendation 阶梯扣次）≈ 2s
- 合计 ≈ 29s

## 2. 已生效 / 已部署的优化

### 2.1 出图内层 4 并发（前端，待手动发版）
- `genImagesForGroup` 由串行改为 `IMG_INNER_CONC=4` 并发池。
- 总并发峰 = 外层 2 worker × 4 = **8 ≤ SLOT_N(10) < 上游 14**，不触发集体 429。
- 收益：单场景 6 图从 ~30~42s 降到 ~10~14s。
- 状态：代码已 `sync_upload.bat` 同步 `<upload-dir>`，**待用户在微信开发者工具手动上传发版**。

### 2.2 scene 模式场景名强制修复（后端，已部署）
- 现象：前端选三个不同场景却渲染出三个"午餐"——根因 sceneMode 返回 `recommendations[].scene` 直接取 AI 回传，AI 偶发把全部场景回成"午餐"，覆盖前端传入值，触发 wx:key 重复 key 警告并显示错乱。
- 修复：`recommendations.forEach(g => g.scene = String(event.scene).trim())` 强制场景名与用户所选一致。
- 前端配套：`wx:key="scene"` → `wx:key="gi"`（index.wxml 112，gi 为 wx:for-index 保证唯一）修复重复 key 警告。
- BUILD_TAG=`2026-08-16.scene-force-fix`；已部署 + invoke 确认 coldstart 生效；前端 wx:key 改动已同步待发版。

### 2.3 前端 TEXT_CONC 1→3（前端，待手动发版）
- 单用户并发≤10 路时 hy3 上游零 429，瓶颈是本地闸门 `TXT_SLOT_N=10`；取 3 占 3/10 槽留余量。
- 多场景时阶段一从 N×1~2s 降到 ~2×1~2s。单场景仍是 1 路（TEXT_CONC 对单场景无效）。
- 已同步 `<upload-dir>`，待发版。观察项：晚高峰若 430 回升则回退 1。

## 3. 已否定的优化方向（探针/代码铁证）

### 3.1 前缀缓存（KV cache）—— 无效
- 方法：CLS 查 `SCENEMODE_TIMING`，取用户连发两次完全相同场景（均午餐，同一用户，间隔 34s，偏好不变）的后端 `afterRegen`。
- 数据：第一次 14565ms / 第二次 13014ms，差距仅 ~1.5s 且方向为略快——完全在 hy3 上游单次推理排队抖动范围内。
- 结论：**CloudBase hy3 上游未透传 KV cache**（文档亦未写）。要求段前移重排无副作用保留即可，无需回退。

### 3.2 砍掉 afterFallbackRewrite 兜底改写轮（主出文内联 reason）—— 不可行
- `capReason4` 证明：无论 AI 返回几字，落库 reason 一律强截/强补成恰好 4 中文字。"reason 4字铁律"由 capReason4 保证，与 afterFallbackRewrite 无关。
- `afterFallbackRewrite` 那轮 AI 的真实作用：**用 AI 重写 reason 使其贴合菜品风味（文言不机械）**，否则退回 `fallbackReason()` 程序通用池。
- 结论：砍掉该轮 = 放弃 AI 贴合型 reason、退回套话池，**用质量换时间且破铁律**，不可行。

### 3.3 主出文 prompt 三段冗余压缩（A 探针）—— 质量不退化但收益小
- 见第 4 节实测。

## 4. A 探针实测：主出文 prompt 压缩质量

- 目的：验证"删命名规范/字段/结构三段冗余举例"后，压缩版 prompt 出文质量是否退化。
- 方法：临时 `probeCompress` 云函数直调 hy3，固定偏好（午餐/偏辣下饭/川菜/猪牛/上海青土豆/忌香菜），手写精简 prompt（保留 reason 4字铁律、截断/连接词吊尾/带馅写馅料核心约束，删大段举例），N=4 评分：合法JSON + dishes=3 + staples=2 + reason 全4字 + 菜名无截断/无吊尾 + 带馅写馅料。
- 结果：**4/4 全通过**。样本示例：`微辣炒上海青 / 土豆炖牛肉 / 辣炒猪肉丝 / 五常大米米饭 / 牛肉热汤面`，完全合规且贴合偏好。
- 字符节省：压缩版 1165 字 vs 原版静态段 1639 字 → **省 474 字（≈29% 静态段）**；整次出文 13s（与原版 13~19s 同量级）。
- 结论：压缩三段冗余**质量不退化**（小样本），可砍约 29% 静态 prefill。
- 诚实提醒：
  1. 474 字 ≈ 省 1~2s prefill，在 13~19s 总耗时占比小，**非瓶颈解**（瓶颈在 decode + 上游排队）。
  2. N=4、单一固定偏好的小样本，真实多场景/多偏好需更大样本验证才能放心上。
- 技术坑：① CloudBase 云函数**隔离运行目录**，探针 `require('../getRecommendation/index.js')` 云端必 `Cannot find module`；② MCP 直调固定 **3s 超时**，单次 hy3 出文含冷启动逼近上限——解法：探针 `timeout:60` + 结果落库规避。
- 善后：探针函数 / 落库集合 / 本地目录已全删；主模块桥接导出已移除并重新部署还原 `scene-force-fix`，线上确认生效。

## 5. CloudBase 免费资源与提速边界

| 能力 | 免费？ | 对出文延迟有用？ |
|---|---|---|
| 混元 hy3（inspire_plan） | ✅ 免费 | 已是主力，单场景 13~19s 物理下限 |
| 混元 hy3-preview | ✅ 免费 | ⚠️ 已于 2026-08-27 移除 |
| DeepSeek / GLM / Kimi / MiniMax / 通义 | ❌ **不免费** | 其他模型不支持免费，需资源点套餐（Token 包已停售） |
| 文生图（混元 image） | ✅ 免费 | 已优化：出图内层 4 并发 |
| 云函数并发实例 | ✅ 免费 | 串行出文瓶颈在 AI 不在函数 |
| 数据库/存储/鉴权 | ✅ 免费 | 与出文延迟无关 |

**结论**：纯免费档能白嫖提速的通道几乎只有已用上的，没有新白嫖口。换免费轻模型提速走不通（除 hy3 外，原 hy3-preview 已于 2026-08-27 移除，其余全付费）。

**唯一可能的"免费"提速口子（需自备 key，非 CloudBase 免费）**：
CloudBase 支持自定义模型（标准版及以上，BaseURL 兼容 OpenAI）。DeepSeek 官方 `deepseek-v4-flash` 自身有免费额度，CloudBase 对自定义模型"不收 Token 费、由第三方计费"。若配成自定义模型，`deepseek-v4-flash` 推理速度通常显著快于 hy3，可能零/极低成本把出文从 13~19s 砍到几秒。代价：引入第三方 key 依赖、脱离 inspire_plan 免费通道、需确认个人版是否支持自定义模型（可能要升标准版）。

## 6. 可行边界总结

- **免费档物理下限**：hy3 单场景出文 ~13~19s（流式/换模型/前缀缓存均不可行），用户侧无解。
- **已生效优化**：出图内层 4 并发（前端待发版，单场景 6 图 30s→10s）。
- **已部署修复**：scene 强制 + wx:key→gi（后端已生效，前端待发版）。
- **不建议再追**：压 prompt（A，省 1~2s 低风险但收益小）、砍兜底轮（B，降质量）。
- **可选下一步**：
  1. 正式采用 A 压缩：替换 `buildTextPrompt` 三段，先 staging 跑 20+ 次多场景对照再上。
  2. 探查 DeepSeek 自定义模型：查套餐是否支持自定义模型 + 实测 `deepseek-v4-flash` 出文耗时对比 hy3（潜在几秒级提速，需自备 key）。
