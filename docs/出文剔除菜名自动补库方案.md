# 出文剔除菜名 · 自动规范化补库方案（③-b / ③-e，AI 判断）

> 状态：方案已实现（待部署验证）  
> 实现进度：autoLexiconFix 云函数已建；getRecommendation ③-b/③-e 已加 fire-and-forget 触发；审核 UI 复用现有 tab 13「探索菜库审核」。仅差部署 + 建 TTL 索引 + 验证。
> 提出：2026-08-18  
> 背景：getRecommendation 后处理已将 ③/③-b/③-c/③-e 统一改为「剔除 + 上报审核队列（dish_feedback）」。  
> 目标：对其中 **③-b 风味前缀、③-e 味型+做法动词冗余** 两类，在后台异步跑轻函数，用 AI 把怪名规范成正确菜名并判定合法性，写入探索审核池（dish_lexicon_pending），供管理员审核入正式菜库（dish_lexicon）复用。  
> 复核结论（2026-08-18）：`奶香蒸南瓜` 非合法菜（"奶香+蒸+南瓜"为 AI 乱拼），`奶香南瓜` 合法（风味+食材家常做法）。③-b 合法与否**无法靠正则判定**，故改用 AI 判断合法性。

## 一、范围澄清（哪些补、哪些不补）

| 后处理分支 | 怪名性质 | 是否进自动补库 |
|---|---|---|
| ③ 弱可疑模式（"乡愁之味"等） | 高度疑似非食词/真怪名 | ❌ 不补（仅上报 dish_feedback） |
| **③-b 风味前缀硬拦截（"奶香蒸南瓜"/"蒜香拌韭菜"等）** | 部分合法（蒜香茄子/奶香南瓜），部分非合法（奶香蒸南瓜） | ✅ **补**（AI 判合法才进） |
| ③-c 小吃场景混入非小吃形态 | 形态错配，非命名问题 | ❌ 不补 |
| **③-e 味型+做法动词冗余（"黑椒炒牛里脊"等）** | 合法菜但命名冗余，可改名 | ✅ **补** |

**结论**：自动补库覆盖 **③-b、③-e** 两类，③/③-c 维持现状（仅上报 dish_feedback，人工核黑名单）。  
**合法判定交由 AI**：③-b 中合法的（蒜香茄子/奶香南瓜）救回补库，非合法的（奶香蒸南瓜）判 skip 不补；③-e 规范后合法性高，正常进库。

## 二、架构原则（沿用现有纪律）

1. **主链路零阻塞（出现即触发）**：getRecommendation 后处理命中 ③-b/③-e 时，**fire-and-forget 异步调 `autoLexiconFix` 云函数**（不 await、`.catch(()=>{})`），把原始怪名 + category 传过去，主出文链路立即 `continue` 剔除。上报/补库失败绝不污染出文（遵守"上报失败绝不阻塞主流程"铁律）。
2. **AI 判断在后台轻函数内**：`autoLexiconFix` 收到怪名后自行调 AI 完成「规范化 + 合法性判定」，主链路不调 AI、不占出文配额。
3. **只进审核池、不直落正式库**：AI 判定合法的规范结果写入现有 `dish_lexicon_pending`（打 `auto:true` 标），由 `manageLexicon` 审核 UI 人工把关后入 `dish_lexicon`，避免自动污染主库。
4. **去重前置**：同一怪名可能高频触发，轻函数入库前按 `kind+'::'+normName` 去重（对齐 `recordFeedback.sinkSelectedToLexicon` 去重模式）。
5. **AI 调用服从限流**：轻函数内调 AI 必须复用现有 `genTextWithFallback`（自动服从 `TXT_SLOT_N` 闸门），不与出文抢文本额度、不触 429。

## 三、集合设计

### 3.1 新增中转集合 `lexicon_auto_pending`（轻函数处理中台）

主链路写（仅落原始信息）、轻函数读改。字段：

```
{
  _id: 自动,
  rawName: '奶香蒸南瓜',         // 原始怪名（主链路写入）
  normName: '',                  // 轻函数 AI 规范化结果（写回）
  kind: 'dish',                  // 固定 dish（当前只补菜）
  category: 'flavorPrefix' | 'flavorVerb',  // 对应 ③-b / ③-e（主链路写入）
  scene: 'today',                // 触发场景（主链路写入）
  status: 'pending' | 'done' | 'skip' | 'failed',
  legal: null,                   // AI 合法性判定：true/false（轻函数写回）
  reason: '',                    // AI 规范说明（给管理员看）
  createdAt: Date.now(),
  processedAt: Date.now(),
  errMsg: ''
}
```

- `status='pending'`：待轻函数处理（主链路写入初值）。
- `status='done'`：AI 判合法且已写入 dish_lexicon_pending。
- `status='skip'`：AI 判非合法（如"奶香蒸南瓜"）或规范后仍疑似怪名，不入审核池。
- `status='failed'`：轻函数 AI 调用异常，可重试。

### 3.2 复用现有 `dish_lexicon_pending`（审核池）

轻函数 AI 判合法后写入，额外带 `auto:true` 与 `category` 标，供审核 UI 区分"机器建议"与"用户探索提交"：

```
{
  name: '蒜香韭菜',            // AI 规范化后菜名
  cuisine: '家常',
  reason: '机器自动规范化：③-b 风味前缀冗余（原「蒜香拌韭菜」）',
  source: 'auto-fix',          // 新增 source 取值，区别于 explore/commit
  category: 'flavorPrefix',
  auto: true,
  valid: false,                // pending 阶段无效
  ts: Date.now()
}
```

`manageLexicon.approve` 现有逻辑 `source: d.source || 'explore'` 已能正确继承 `auto-fix`，**无需改后台**即可入 `dish_lexicon`。

### 3.3 现有 `dish_lexicon`（正式库，不直写）

仅经 `manageLexicon.approve` 写入，字段沿用现有结构（name/cuisine/reason/source/exploreDir/valid/ts/originPendingId）。

## 四、AI 规范化 + 合法性判定（轻函数核心，不再用确定规则）

**废弃原"正则剥动词"确定规则**——③-b 合法与否（奶香南瓜 vs 奶香蒸南瓜）正则无法判定，改由 AI 在轻函数内完成：

- **输入**：`rawName`（如"奶香蒸南瓜"/"黑椒炒牛里脊"）、`category`。
- **AI 任务**：
  1. 规范化：输出该怪名对应的**正确、真实存在的中餐菜名**（无则输出空）。
  2. 合法性：判定规范后菜名是否真实存在、是否适合收录（排除明显 AI 乱拼/非食词）。
- **判定结果**：
  - 合法 → `legal:true`，`normName` 写回，入 dish_lexicon_pending。
  - 非合法/无法规范 → `legal:false`，`status='skip'`，不入库（如"奶香蒸南瓜"→skip）。

**保底**：AI 返回仍命中 `weakSuspect`/`flavorVerbHit`/黑名单词表，则强制 `skip`（AI 不可全信，规则兜底）。

## 五、轻函数 `autoLexiconFix` 设计

- **类型**：独立云函数。触发方式 = **主链路命中即调**（见第六章），不依赖定时。
- **AI 模型路由（函数内重试）**：
  1. 调 **`hy3`**（仅此通道；hy3-preview 已于 2026-08-27 移除）。
  2. 若**超时**（或限流 429）→ 由 `genTextWithFallback` 经 aiGateway 兜底 custom/[SF]（限流退避重试 1 次，不跨函数、不抛给用户）。
  3. 仍失败 → 该条置 `failed`，记录 errMsg，不阻塞其他条。
  > 注：个人版 `hy3-preview` 已于 **2026-08-27 移除**，统一只留 `hy3`（由 aiGateway 按 mode 编排 hy3→自定义→[SF] 降级链）。
  > 所有 AI 调用经 `genTextWithFallback`，服从 `TXT_SLOT_N` 闸门。
- **流程**：
  1. 收到 `{ rawName, category, scene }`（单次调用，主链路触发）。
  2. 去重前置：查 `dish_lexicon` + `dish_lexicon_pending` 是否已存在该 `rawName` 的规范结果，命中则直接 `done`（不重复调 AI）。
  3. 调 AI（preview→hy3 降级）→ 得 `normName` + `legal`。
  4. `legal:true` → 写 `dish_lexicon_pending`（带 `auto:true`）+ 本记录 `done`。
  5. `legal:false` / 兜底命中 → `skip`。
  6. 全量 try/catch，异常置 `failed`（遵守修复纪律，不吞根因，记录 errMsg）。
- **BUILD_TAG**：顶部加 `BUILD_TAG='2026-08-18.auto-lexicon-fix'`，每请求 log。

## 六、主链路改动（getRecommendation 后处理）

在 ③-b / ③-e 的「剔除 + 上报」分支中，**额外 fire-and-forget 异步调 `autoLexiconFix`**（不 await、失败仅 warn，不阻塞出文）：

```js
// ③-b / ③-e 剔除 + 上报 dish_feedback + 异步触发 AI 补库（出现即触发，不阻塞）
if (db && OPENID) {
  await reportSuspiciousName(db, OPENID, nm, '拼凑', g.scene); // 原有上报
  try {
    cloud.callFunction({
      name: 'autoLexiconFix',
      data: { rawName: nm, category: '<flavorPrefix|flavorVerb>', scene: g.scene }
      // 不 await：fire-and-forget，出文链路立即 continue
    }).catch(() => {});
  } catch (e) { /* 触发失败绝不阻塞主流程 */ }
}
continue;
```

> 注意：③/③-c 分支**不触发** `autoLexiconFix`，维持仅上报 dish_feedback。  
> 中转集合 `lexicon_auto_pending` 改为**可选**（若需审计/重试可追溯则保留，轻函数内自行写回状态；若简化可只在轻函数内存处理、失败置 failed 留痕于日志）。
