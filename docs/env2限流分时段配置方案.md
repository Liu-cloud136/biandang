# env2 生文 / 生图限流分时段配置方案

> 状态：设计稿（仅方案，**未改代码**）
> 日期：2026-08-24
> 背景：env2 后端补全链路（bypassGenDish 串行链 + 各下游 10 分钟 timer）已稳定，但混元 **生文（hy3 文本）** 与 **生图（hunyuan-image）** 两个上游存在限流（429）。实测并发级参数已调优，但限流本质是**时间窗口速率配额（分时段）**，需在方案层明确"不同时段怎么配"。

### 0. 限流边界澄清（用户确认）
- **平台名义额度 QPS=500 是每个环境各自独立的**（env1/env2 各有 500，互不挤占）。
- **但混元上游是公共池**：除了你家环境，还有**别的调用方（全网其他腾讯云用户）共用同一个混元服务**。当公共池被别人（或全网高峰）抢满时，即使你这边没超自己环境的 500，也会 429。
- 即：**实际能跑多少 = min(自己环境 500, 混元公共池实时余量)**。别人用满了 → 你这边被限。
- **分时段依据 = 混元公共池的全网忙闲节律**，不是你家环境自身配额：
  - 深夜/白天（全网闲）→ 公共池空余多 → env2 可放心跑当前稳健值。
  - 饭点/晚高峰（全网暴涨）→ 公共池被挤满 → env2 即使没超自己 500 也易 429。
- **结论**：饭点降速/跳过，本质是**不与全网高峰硬刚**，等公共池空了再补。

## 1. 已验证的事实（实测结论）

### 1.0 关键前提：名义额度按环境独立，但实际受混元公共池约束

- 平台**名义额度 QPS=500 是每个环境各自独立**的（env1/env2 各 500，互不挤占）。
- **但混元上游是公共池**：除你家环境外，还有**全网其他调用方共用同一个混元服务**。公共池被别人抢满时，你这边即使没超自己 500 也会 429。
- **推论**：env2 实际能跑的吞吐 = min(自己环境 500, 混元公共池实时余量)。限流调优不能只看 env2 自身，必须**按公共池全网忙闲节律分时段**——这正是本文档的核心。

### 1.1 生文（hy3 文本模型）
> 注：以下实测于 **昨晚 ~23:00（深夜闲时）**，且 env2 单独跑。因为环境独立，该阈值即 env2 这个环境的真实安全线，**忙时也不会因他人挤占而更糟**（不共享）。

| 参数 | 结果 |
|------|------|
| SLOT_N=12（瞬时） | 满屏 429，限流恶性循环 |
| SLOT_N=5 | 0 个 429，24 条 1.6s 跑完 |
| 结论 | 文本并发阈值 ≈ **10 内安全**，取 5 留余量 |

- 文本限流偏 **并发级**（瞬间并发数），但底层仍是速率配额。
- 当前所有文本下游（ingredients/steps/text/tips/enrich/nutrition）已统一 SLOT_N=5 + 循环补齐 + 串行链（全局并发 ≤5）。

### 1.2 生图（hunyuan-image 模型）
> 同样为深夜闲时实测。生图比文本严，但仍属 env2 自身额度内问题。

| 并发 | 结果 |
|------|------|
| CONCURRENCY=10 | 成功 1/14（满屏 429） |
| CONCURRENCY=3 | 成功 6/14（仍 429） |
| CONCURRENCY=2 + 5/10/15s 退避 | **7/7 全成功，0 个 429** |

- 生图限流是 **时间窗口级（每分钟配额）**，比文本严得多。
- CONCURRENCY=2 + 429 指数退避（5/10/15s）已稳跑。

### 1.3 触发拓扑（影响配额消耗节奏）
- `bypassGenDish` 每 10 分钟入库 → **串行链** 依次触发：
  `AiEnrich → NutritionEst → GenImage → GenIngredients → GenSteps → Text → GenTips`
- 串行链保证**任意时刻只有 1 个下游在跑**，全局文本并发 ≤5、生图并发 ≤2。
- 各下游还有独立 **10 分钟 timer** 兜底补缺（与串行链可能重叠，但都受 SLOT_N/CONCURRENCY 约束）。

## 2. 限流的真实形态

CloudBase AI / 混元上游的限流表现为：

- **名义额度 QPS=500 按环境独立**：env1/env2 各有 500，互不挤占。
- **实际受混元公共池约束**：公共池被全网其他调用方抢满时，你这边即使没超自己 500 也 429。env2 实际能跑的吞吐 = min(自己 500, 公共池实时余量)。
- **并发上限（INFlight）**：实测文本 ~10 内安全、生图 ~2 安全——这是深夜闲时（公共池空）测到的 env2 安全线，**忙时公共池满时会更低**。
- **时间窗口速率**：生图表现出的"窗口级 429"说明上游对 image 模型按时间窗口限流（每分钟配额），而非纯并发。

> 关键认知：单纯降并发只能缓解"瞬时并发"型限流；对于**时间窗口速率型**（生图）和**公共池被抢满型**（全网高峰），必须**按时间平滑吞吐 + 分时段避让**（令牌桶 / 速率控制器 + 饭点降速），否则一波打完公共池余量 → 全 429 → 等下个窗口。分时段依据是**混元公共池的全网忙闲**，不是自家环境配额。

## 3. 过渡方案（可选，非最终）—— 硬编码两档降速

1. **维持当前稳健值即可**：深夜闲时实测已证明 SLOT_N=5（文本）/ CONCURRENCY=2（生图）在公共池空余多时稳跑，**不需要闲时提速**（提速徒增 429 风险，且公共池余量不归你独占）。
2. **饭点降速避让全网高峰**：饭点（`isPeakHour` 11–13、17–19）公共池最易被全网抢满，env2 **跳过生成 / 降速**。

## 4. 最终实现形态：自适应速率控制器（推荐落地）

> **本方案以本节为最终目标实现。** 硬编码时段表（第 3 节）不够鲁棒——公共池忙闲由全网决定，无法靠手维护时段表精确匹配；更稳的是**纯自适应**：让 env2 自己探测公共池余量，自动收敛到"最大不 429 吞吐"。

### 4.1 为什么自适应最适合当前场景
- 公共池被**全网其他调用方**共用，忙闲节律不可预测（饭点只是大致高峰，具体实时余量未知）。
- 自适应无需知道确切配额/时段，靠"429 ⟹ 降速、连续成功 ⟹ 提速"自动贴合公共池实时余量。
- 闲时自动跑满（接近当前 SLOT_N=5 / CONCURRENCY=2 安全线），饭点公共池满时自动降到极低速，**天然实现"饭点降速避让"且无需手维护时段表**。

### 4.2 算法规格（通用 `rateLimiter`）

维护一个**动态速率 `rate`**（单位：每秒允许通过请求数，等效令牌桶 refill 速率），并配硬上限兜底：

```
state:
  rate          // 当前速率（初始 = rateInit，如 5 或 2）
  rateMax       // 速率天花板（防振荡击穿后无限提速），如 8（文）/ 4（图）
  rateMin       // 速率地板（如 0.5），避免降到 0 卡死
  windowCalls   // 最近 60s 已发调用计数
  windowStart   // 窗口起始时间戳
  successStreak // 连续成功次数

acquire():
  // 1) 时间窗硬上限：最近 60s 调用数超 windowCap → sleep 到窗口重置（防公共池被一波打满）
  if now - windowStart >= 60000: reset windowCalls=0, windowStart=now
  if windowCalls >= windowCap: sleep until windowStart+60000; reset
  // 2) 令牌桶：按当前 rate 限速（等效串行链里的"取下一个待处理项"闸门）
  wait until token available (refill = rate tokens/sec, burst = rateMax)
  windowCalls++

onSuccess():
  successStreak++
  if successStreak >= K:            // 连续 K 次成功 → 试探提速
    rate = min(rate * 1.1, rateMax)
    successStreak = 0

on429():
  rate = max(rate * 0.6, rateMin)   // 遇 429 → 降速 40%
  successStreak = 0
  backoff(5s → 10s → 15s...)        // 退避等公共池恢复（图可更长）
```

### 4.3 与现有机制的衔接
- **替换现有的固定并发闸门**：语义上替代 `pool(list, SLOT_N, ...)`（文本）和 `CONCURRENCY` + 手写退避（生图）。即在"取出下一个待处理项"处 `await acquire()`。
- **串行链不变**：任意时刻只有 1 个下游在跑，自适应只在单下游内控速率。
- **循环补齐不变**：MAX_MS 超时约束保留，自适应只决定"多快消费"，不影响翻页。
- **10 分钟 timer 不变**：兜底补缺仍靠它；自适应保证每次 timer 触发都在公共池余量内平滑跑，饭点自动降速、闲时自动跑满。
- **`isPeakHour()` 可保留作"硬跳生成"**（饭点完全不新生成，纯避让），但补缺 timer 不再需要手降速——自适应会自动在饭点降到极低速补，闲时跑满。二者不冲突。
