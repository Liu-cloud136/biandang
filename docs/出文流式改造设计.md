# 出文流式改造设计（路线2：云端流式 + 前端增量渲染）

> 日期：2026-08-16 ｜ 目标：`getRecommendation` 出文从「全部场景出完才整体返回」升级为「场景逐个就绪即推前端」，前端逐场景渲染，降低用户体感等待。
> 背景：用户此前试过 token 级流式「不能用」，根因是遍历方式错（`res` 当 asyncIterator / 找 `getReader`），正确写法为 `for await (const text of res.textStream)`。探针 `probeStream` 已验证 hy3 在 Node SDK 下 `res.textStream` 可用、`chunkCount=10`、可拼出完整文本、可取 `usage`。

## 一、现状与关键约束

1. **架构**：`getRecommendation` 是 **Event 云函数**；前端 `pages/index/index.js` 用 `wx.cloud.callFunction` 调，且采用**单场景串行模式**（每个场景一次 callFunction，前端传 `event.scene`）。主出文核心链路：`genTextForScenes`（8671）→ `genTextWithFallback({primary:'hy3'})`（363）→ `parseRecommendations(text)`（5769）→ 结构化数组 `{groups:[{scene,dishes:[{name,reason,calories,...}],staples,drinks}]}`。
2. **返回是结构化 JSON，非纯文本**。`extractJson`（5741）用 `JSON.parse`，**不容错**——不完整 JSON 返回 null。这是「token 级增量解析 JSON」不可行的最大障碍。
3. **前端已具备分步渲染能力**：`_commitResultRender()`（603）渲染 `recs[0..k)` 连续已就绪场景；`genTextForScene`（723）逐场景 callFunction，`recs[gi]` 整场景到位才填。
4. **环境约束**：env1 个人版（非标准版），`wx.cloud.extend.AI` 前端直连方案（文档小程序写法）**无后端逻辑、不可用**于推荐链路（权重/安全/扣次全在云函数），故走「云函数内流式 + SSE 推前端」的路线2。

## 二、方案选型

### 方案 X（推荐，场景级 SSE，低风险）⭐
把 `getRecommendation` 改造成 **HTTP 函数 + SSE**（`text/plain; charset=utf-8` + `Transfer-Encoding: chunked`）。流程：
- 云函数内 `Promise.all` 各场景 `genTextForScenes`，但**每完成一个场景即 `res.write(JSON.stringify({type:'scene',scene,data:group})+\n)`** 推前端；全部完成后 `res.write({type:'done',historyId,...})` 并 `res.end()`。
- 前端用 `wx.request({url, enableChunked:true, onChunkReceived})` 累积 SSE 片段，每收到一个 `type:'scene'` 即把该场景填入 `recs[gi]` 并调 `_commitResultRender()` —— **复用既有分步渲染，零新增前端渲染逻辑**。
- AI 文本生成本身仍 `generateText`（一次性拿完整 JSON，保结构正确），**不逐 token 解析 JSON**（规避 extractJson 不容错风险）。「流式感」来自「场景逐个就绪即显示」，而非 token 级。

**收益**：体感从「全场景出完才显示」→「早场景先出先显示」（出文耗时若被分摊，首屏可见时间大幅下降）；复用 `dedupCrossScene`/`_commitResultRender`；不破坏结构化解析。
**风险**：需把 Event 函数改 HTTP 函数（部署/路由变化）；SSE 在微信小程序 `wx.request` 需 `enableChunked:true`，需真机验证；前端要加 SSE 累积解析。
**改动量**：中（云函数入口改 HTTP+write；前端加 onChunkReceived + 场景回填）。

### 方案 Y（真·token 级流式，高风险）⚠️
云函数内 `for await (const text of res.textStream)` 累积 token，边收边尝试解析。因 `extractJson` 不容错，必须自研**流式 JSON 增量解析器**（增量状态机 / 容错 parse），且前端要边收纯文本边做"肉眼可见的菜名"渲染（而非结构化卡片）。
**风险极高**：JSON 未闭合时解析崩溃、字段半截显示错位、营养/理由割裂、调试地狱。且你出文要做内容安全/扣次，纯文本流难做原子化入库。
**结论**：不推荐，除非用户坚持"字一个个蹦"的对话式体验（那已偏离"结构化推荐卡片"产品形态）。

### 方案 Z（伪流式，零改造）⚠️
前端在 callFunction 等待期间播放骨架动画 / 进度文案。不改云端。
**结论**：不降真实延迟，仅心理安慰，价值低，仅作过渡。

## 三、最终实施方案（方案 X，单函数双模式 + 抽核心）

### 3.0 技术阻塞点（已澄清）
- `getRecommendation` 是 **Event 函数**；CloudBase 一个函数只能 Event **或** HTTP，不能共存。
- 核心出文 `genTextForScenes`（8671）定义在 `exports.main` 闭包内，依赖 `prefs/chosenNames/tasteShiftCuisine/cfPromise/TEXT_CHUNK/db/app` 等十几个变量，**无法被新 HTTP 函数 require 复用**。
- 因此必须做**一次受控重构**：把"场景出文核心"抽成顶层函数，Event 与 HTTP 两入口共用。

### 3.1 重构：`buildSceneRecs(ctx, scenes)`（顶层）
- 把 `genTextForScenes` 及其依赖的闭包变量聚合为 `ctx = {db, app, prefs, chosenNames, recentNames, blocked, tuning, tasteShiftCuisine, cfPromise, TEXT_CHUNK, ...}`，抽到 `getRecommendation/index.js` **顶层**。
- `exports.main`（Event 分支）照旧调 `buildSceneRecs(ctx, chunk)`，`return` 结构不变 → **Event 模式零行为变化**。
- 新增顶层 `async function runFullSSE(ctx, allScenes, res)`：复用 `buildSceneRecs`，逐 chunk 完成后 `res.write(JSON.stringify({type:'scene',gi,data:group})+'\n')`，结束 `res.write({type:'done',historyId,...})` + `res.end()`。

### 3.2 新建 HTTP 函数 `getRecSSE`（独立）
- 类型 HTTP + `scf_bootstrap`（`streamProbe` 已验证可跑 SSE）。`index.js` 内：`require('../getRecommendation/index.js')` 取 `exports.buildSceneRecs` / `exports.runFullSSE`（或把函数 export 出来）。
- `exports.main(req,res)`：解析 `req.query/body`（scene 列表 + usedStaples/usedDishes + 定位 + 探索目标），重建 `ctx`（DB 读取 + 权重计算复用 `getRecommendation` 的导出段），`res.setHeader` SSE，`runFullSSE(ctx, scenes, res)`。
- **`getRecommendation` Event 函数保持完全不动**（仅新增顶层导出），老 9 个 action 的 `callFunction` 调用零改动 → 风险隔离。

### 3.3 前端改造（仅主出文 `index.js` 的 `onDecide`/`genTextForScene`）
- 新增 `sys_config.stream_v2`（默认 false = 旧模式）。true 时：`onDecide` 改用 `wx.request({url:HTTPS_SSE, enableChunked:true, onChunkReceived})`；累积 buffer 按 `\n` 切分，解析 `type:'scene'` 填 `recs[gi]` + `_commitResultRender()`；`type:'done'` 触发 `commitRecommendation`（原逻辑平移）。false 时走原 `callFunction` 串行。
- 失败场景（`_err`/`430`）提示文案不变。

### 3.4 回退
- `sys_config.stream_v2=false` → 前端回退旧 `callFunction`；`getRecSSE` 函数/路由可留可删，不影响 Event 链路。

### 3.5 实施步骤（顺序）
1. 抽 `buildSceneRecs` 顶层 + `exports.main` 改调（Event 行为不变）→ 部署 `getRecommendation`，验原 9 action 正常。
2. 新建 `getRecSSE` HTTP 函数壳 + `scf_bootstrap` + 路由 + 权限（登录用户）→ 部署，curl 验 SSE 多段。
3. 前端 `onDecide` 加 SSE 分支（stream_v2 开关）→ 真机验逐场景显示 + `commitRecommendation` 正确扣次。
4. `stream_v2=true` 灰度；观察日志；异常秒回退 false。

## 四、验证清单
- [ ] 真机 `wx.request({enableChunked:true})` 收到多段 SSE（非一次性）。
- [ ] 多场景顺序不受 SSE 乱序影响（早/午/晚 区块位置正确）。
- [ ] `dedupCrossScene` 跨场景去重仍生效（午晚同名被剔除）。
- [ ] 内容安全 / `commitRecommendation` 扣次在 `done` 后正确执行一次。
- [ ] 失败场景（430/`_err`）前端提示文案不变。
- [ ] `sys_config.stream_v2=false` 可秒回退。

## 五、结论
路线2 可行，但**不要做 token 级 JSON 增量解析**（extractJson 不容错 + 产品是结构化卡片）。最优是**方案 X：场景级 SSE**——复用既有分步渲染，把"全出完才显"升级为"逐场景显"，体感收益足够、风险可控、可灰度回退。
