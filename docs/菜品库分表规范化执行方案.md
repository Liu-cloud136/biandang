## 一、背景与目标

### 1.1 为什么现在要动数据

阶段3 要求 env1 在**几千道菜、全量数据**上做到零延迟/零额度/高并发的纯查表推荐。查表的前提是：数据能按"名称"稳定唯一取到、各维度（推荐理由/做法/清单/贴士/点评/难度/图片/菜系/口味）能**按需低成本读取**。现状不满足：

| # | 现状问题 | 后果 |
|---|---------|------|
| 1 | `dish_lexicon` 大宽档：`ingredients[]`、`profile` 塞在主词条里 | 排序只想要菜系/口味时被迫背大字段，读放大 |
| 2 | `dish_guide_pending` 五维混合（guide/steps/review/difficulty/tips/ingredients），正式库 `dish_guide` 只落 `guide` | 审核入库即丢 steps/tips/review/difficulty/ingredients，维度数据资产流失 |
| 3 | 无 schema 定义真源，建表靠各函数散点 `createCollection` | 字段结构只能从代码反推，改结构靠人肉协调 |
| 4 | 同一语义多处重复（营养：`dish_nutrition` / `dish_mirror.nutrition` / 代码常量 `DISH_NUTRITION`） | 一致性无保证 |
| 5 | 字段命名驼峰/蛇形混用（`imageUrl`/`mainIngredient`/`originPendingId` 历史遗留） | 无法建立统一读写层 |

### 1.2 目标

1. 以**规范化菜品名**（菜名/饮品名/小吃名/汤羹名…）为全链路唯一识别标识，即各分表 `_id` = `normLexName(name)`。
2. 按**读取频次分层**拆分：排序热字段留在热表，内容详情进冷表、命中后按需懒加载。
3. 建立 schema 真源（本文档即真源），统一幂等建表。
4. 为阶段3 铺路：排序只读热表 → 打分定序 → 对 top N 按需取冷表 → 模板拼装。

### 1.2.1 目标达成核验（2026-08-26 阶段0~6 完成后核实）

| # | 目标 | 状态 | 核实说明 |

## 二、可行性结论

**可行，且是阶段3 的必要前置。** 依据：

1. **已有先例**：`dish_nutrition` / `dish_guide` / `dish_images` 已是 `_id=菜名` 独立分表（`cloudfunctions\manageLexicon\index.js:126-133`）。项目骨子里已在走"名称即主键"路线，本次只是把它贯彻到底。
2. **读取模式已验证**：画像增强分 `aiMatchBonus` 用 `where({name:_.in(候选名数组)})` 一次批量查（`docs\env2补充env1菜谱库.md:148`），分表后冷表同样用 `_.in()` 批量取，延迟可控。
3. **数据量支持**：几百~几千条，云开发文档型数据库完全承载，不需要关系型 JOIN 能力——用主键精确取/ `in()` 批量取即可替代。
4. **风险可控**：增量改造（见第五章），不推倒重来，env1 主链路（出文 hy3 流式）全程不受影响。

**关键约束（红线）：不做"每字段一表"的微拆。** 拆成 8~9 张维度块表即可；再细拆会让阶段3 每次出文跨集合查询次数失控（云开发单函数读库次数有配额），反而违背"零延迟"目标。

## 三、设计原则

| 编号 | 原则 | 说明 |
|------|------|------|
| P1 | 名称即主键 | 各分表 `_id` = `normLexName(name)`（**弱归一**，D12），主表以 `norm_id` 对齐（D1）；复用现有 `normLexName`（折叠空白+去首尾），与存续表 `_id` 同口径。**跨品类同名即同一实体**（D2）：归为一个 `_id`，维度合并，category 冲突取最新/最高频 |

| P3 | 增量不推倒 | 新集合幂等创建；旧集合字段在双写过渡期保留，稳定后清理归档；不重建云环境、不重写主链路 |
| P4 | 读写单源 | 消费端一律读新集合；写入端（bypass 链 / syncFromEnv2 / manageLexicon / recordFeedback）在过渡窗内新旧双写，过渡期结束关旧 |
| P5 | 命名 snake_case | 集合+新字段一律 snake_case；历史驼峰字段在使用点做一次映射，不强制回溯存量数据 |
| P6 | 全链路可校验 | `checkSevenPiece` 与巡检脚本按新 schema 判维度完整性，缺失可对账、可补算 |

## 四、目标 Schema（env1 正式库）

> 集合名均为 snake_case；主表以 `norm_id`（规范化菜品名）为查询主键，各分表 `_id` 与 `norm_id` 对齐。
> 对比现状：`dish_lexicon` 保留为主表（热层）并做字段瘦身；新增 5 张内容分表；`dish_nutrition`/`dish_guide`/`dish_images` 存续并在结构上补齐。

## 六、关键设计说明

### 6.1 存量 `dish_lexicon` 主键兼容策略（D1 已确认）

云开发文档 `_id` 不可原地修改。存量自动 ID 保留：主表新增 `norm_id`（= `normLexName(name)`）作统一查询主键，新写入必填、存量搬家时补齐；**各分表一律以 `norm_id` 为 `_id`**。主表查询保持 `where({valid:true})` 全量拉取 + 内存 join（现有 `getRecommendation\index.js:5854` 已是全量拉 name/kind 后在内存按名操作）——当前数据量（几百~几千）内存 join 完全可行，与 `aiMatchBonus` 现网做法一致。

### 6.2 阶段3 查表读取链路（目标形态）

```
# 一次推荐出文（零 AI 调用）
hot = SELECT * FROM dish_lexicon WHERE valid=1             # 主表全量(内存缓存，分钟级超时刷新)
profile = dish_profile._id IN (hot.norm_id)               # 打分用
nutri   = dish_nutrition._id IN (top_candidates)          # 近热，可延迟
ranked  = score(hot × profile)                            # 排序(画像增强+探索分+UCB 沿用)
top     = ranked[0..5]
cold    = { recommend/guide/ingredients/tips/review/image }._id IN (top)   # 命中后一次取齐
text    = render_template(top, cold)                       # 模板拼装出文
```

### 6.3 命名与字段映射

- 新字段一律 snake_case（`meal_time`、`explore_dir`、`image_url`、`is_veg`、`step_no`）。
- 历史驼峰字段（`imageUrl`、`originPendingId`、`mealTime` 等）在读写 util 内做映射，不做存量数据迁移，避免无谓全量改写。

### 6.4 用户侧菜名桥接协议（原文 ↔ norm_id）

- 用户侧所有数据（`user_preferences` / `recommend_history` / `favorites` / `gen_records` / `exposure_mirror` / 购物历史）**仍按原文菜名存取**，不做存量迁移，用户侧零改动。
- 出文/读取侧统一桥接：拿到原文菜名 → `normLexName(name)`（弱归一）→ 以 norm_id 查分表；写回反馈时原样存原文名（D12）。
- env2 `dish_mirror` 内部保留强归一（去重池口径，`bypassGenDish.normalizeDishName`），**不参与 env1 主键**；`syncFromEnv2` 写 env1 时 `norm_id` 一律由弱归一生成本地生成。两侧口径不同为有意设计：强归一防 env2 重复生成，弱归一供 env1 稳定主键。

### 6.5 阶段3 库扩充路径（D13）

主表系作为查询真源后，全量数据来源三路并进，按序执行：
1. env2 持续生成灌入（现有 `dish_mirror` → syncFromEnv2 → 审核 → 分表）；

目标规模：几千道菜、全维度覆盖后进入阶段3（零 AI 查表）。
