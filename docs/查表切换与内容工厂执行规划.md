## 一、背景与已定决策（2026-09-06 会话拍板）

| #   | 决策                                                       | 依据                                                                                                     |

| 7   | **新鲜感三板斧**（一菜多荐 / 每日菜单剧本 / 时令选题包）：AI 全部离线干活、成果落库，出菜路径零改动 | 用户拍板"要新鲜感"；env1 侧 AI 闲置算力再利用，不增加任何请求延迟                                                                 |

- 报告：`scripts/output/lookup_hitrate_report_20260906.md`；仿真器 `scripts/lookup_hitrate_sim.js`（--pilot/全量可复跑）

## 三、目标架构

```
【请求路径】env1 主推荐 = 零 AI 纯查表（毫秒级）
  用户请求 → getRecommendation(mode=lookup) → 候选池打分排序 → 图片缓存 → 返回
                                              ↓ 未命中（预期<1%）
                                    相近菜兜底 / 转.live 一单（熔断器在）

【定制功能】冰箱 / 剩菜 / trySomething = 保留实时 AI（低频，用户预期有等待）
  冰箱中期增强：先库内食材交集检索（秒回现成菜）→ 不足再 AI 定制（二期）

【后台工厂】AI 只做生产，永不出现在用户等待里
  env2：覆盖率矩阵出缺口 → 定时生成 → mirror 六件套 → 审核 → 入库 env1
  env1：差评反馈 → reworkRegister → 返工重生成 → 复核 → 自动覆盖
        周检（全库重核）/ 波动复扫 / 图片 miss 补生成（已就绪）
```

## 四、阶段计划

### 阶段 1：查表切换（最高优先级，预计 1 天）

| 步骤          | 内容                                                                                              | 验收                                       |
| ----------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 1.1 补夜宵标签   | **口径（用户 09-06 两轮更正后定稿）：夜宵标签只打主食（含汤羹类如需）补缺口；小吃、饮品是独立场景，一律不打夜宵标签**。主食缺口规则要求 ≥2                    | 重跑仿真夜宵场景命中（`lookup_hitrate_sim.js` 场景子集） |
| 1.2 全量回归    | 重跑 359 组仿真确认 100% 或 ≥99.7% 且无场景级缺口                                                              | 报告归档 output/                             |
| 1.3 拨开关     | `sys_config/recommend_mode` → `{mode:'lookup', ratio:100, autoCircuit:true, autoFallback:true}` | invoke 返回 lookup_mode=lookup；面板数字正常      |
| 1.4 观察 3 天  | 每日看 [lookup-mode] 日志（pool 大小/耗时/fallback 次数）与熔断器状态                                              | fallback 率 0；无 circuit breaker 触发        |
| 1.5 新鲜感调优   | **用户拍板"要新鲜感"**：观察期内调高探索位概率（E6 被埋没新菜）、确认曝光降权与轮换在工作，让"每天来的老用户"看到的组合有变化                            | 主观验收：连续多天请求，菜目组合不重样                      |
| 1.6 沉默 live | 观察期满无异常即保持 lookup 常态；live 分支代码保留（红线不动），作为熔断兜底                                                   | —                                        |

**回滚**：`recommend_mode` 改回 live 即可，秒级生效，无需发版。

### 阶段 2：新鲜感三板斧（AI 离线内容，出菜路径零改动）

> 原则：AI 在夜间/批处理把"新鲜感"提前做好落库，白天请求路径仍纯查表读库，延迟不变。

| 步骤         | 内容                                                                                           | 验收                                          |
| ---------- | -------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 2.1 一菜多荐   | AI 离线给 2925 道菜每道生成 4~5 版不同风味的推荐语（咸鲜下饭/馋人/应季等），落库（不覆盖原 4 字 reason，保留兜底）；出菜按「日期+openid 哈希」轮换取用 | 抽 30 道人工过目文风；同一道菜不同日期展示语不同                  |
| 2.2 每日菜单剧本 | 每日凌晨任务：AI 结合天气/季节/时令，从查表候选池编排 2~3 套"今日吃法"（早/午/晚/夜宵）落库；白天请求取当日剧本，个人忌口与偏好照常在剧本内硬过滤             | 请求仍为查表级速度；连续多天剧本不重样；剧本生成失败时静默退回普通查表（绝不阻塞出菜） |
| 2.3 时令选题包  | AI 按 24 节气 + 天气模式（降温/下雨）预生成主题，给对应菜打时令标签，查表按时令加权（复用现有 weather_ctx 调权通道）                       | 立秋/降温日的推荐确实出现时令菜                            |

**落地注意**：2.2 剧本只决定"今天这批从哪个池子出"，个人偏好过滤仍由查表引擎完成——AI 编排、查表执行，分工不变。

### 阶段 3：食材清单展示分组（预计 0.5 天，前端 + 展示层）

| 步骤       | 内容                                                                        | 验收                  |
| -------- | ------------------------------------------------------------------------- | ------------------- |
| 2.1 调料识别 | 展示层引入 seasoning_library（name+alias 白名单精确匹配）；**dual/复合酱料（豆瓣酱等）不进调料组，宁少勿错** | 抽 30 道菜人工核对分组       |
| 2.2 前端展示 | 菜详情清单分「食材（带量）/ 调料（无量，顿号平铺）」两组；数据层 dish_ingredients 零改动                    | 截图评审；复核口径不受影响（数据未动） |
| 2.3 出菜接口 | 若前端不便过滤，则在 getRecommendation 返回体加 display 分组字段（add-only）                  | 新旧字段并存，前端灰度可回退      |

**红线**：不动 dish_ingredients 数据、不动 AI 复核口径——分组纯展示层。

### 阶段 4：env2 缺口驱动扩充菜品库（预计分批长期运行）

| 步骤        | 内容                                                                                      | 说明                                          |
| --------- | --------------------------------------------------------------------------------------- | ------------------------------------------- |
| 4.1 覆盖率矩阵 | 离线脚本：食材大类(20)×场景(7)×类别（荤/素/主食/汤/饮）逐格统计"查表可用优质候选数"，阈值 N（建议每格 ≥5）出缺口清单                    | 复用 lookup_hitrate_sim 的输入空间与门配置手法（只读统计，不改门） |
| 4.2 定向生成  | 按缺口清单生成一批（**每批 ≤100 道**，先大缺口后长尾）；env2 复开生成管道（GEN_DISABLED 解除，bypassGenDish 定时器按批启用而非常开） | 08-29 曾因质量低下停用；现质量闸门齐备（复核闭环/命名规范/波动复扫）故复开   |
| 4.3 补齐与送审 | mirror 六件套补齐（图/菜系/推荐语/营养/步骤/食材）→ review-web 审核（强重复先裁决→批量通过→怪名筛）                         | 沿用 1695 道 Cookbook 批的成熟流程                   |
| 4.4 入库与刷新 | AI 复核通过 → 入库 env1 → 重跑覆盖率矩阵 → 有缺口再排下一批                                                  | **产量对齐人工审核消化速度（用户确认亲自审核每批）**；审核是瓶颈，生成不是     |
| 4.5 首批范围  | 夜宵主食标签补齐（衔接阶段 1，仅主食/汤羹类）+ 矩阵首轮缺口                                                        | 用户拍板后启动                                     |

**命名与质量红线**（沿用既有规范）：可选项必须有"以该物为主料的风味菜"；米种米饭可独立成菜；焖饭必须带真实配菜；R-Sync-04 整菜丢弃口径；reason 4 字文言口径。

### 阶段 5：用户反馈闭环（预计 0.5 天，前端为主）

| 步骤       | 内容                                                                            | 说明                         |
| -------- | ----------------------------------------------------------------------------- | -------------------------- |
| 5.1 前端入口 | 菜详情加"举报/不喜欢"按钮（复用 dish_feedback 或直达 reworkRegister）                           | 已有 submitDishFeedback 通道可选 |

| 5.3 忌口联动 | 举报含过敏原类 → 同时写用户 avoid                                                         | 查表路径忌口硬过滤即刻生效              |

### 阶段 6（二期，不排期）：冰箱检索层 + 周表查表化 + 图片抽检

- 冰箱模式加"库内食材交集检索"前置层（2925 道食材结构化已具备），秒回现成菜，AI 只补长尾

- **图片抽检重画**（用户 09-06 拍板放二期）：随机抽 20~30 张人工过目，明显不符的标记重生成

## 五、风险与对策

| 风险                            | 对策                                                     |
| ----------------------------- | ------------------------------------------------------ |
| 查表未命中组合（上线后真实输入超出仿真空间）        | 熔断器+autoFallback 兜底转 live 一单；fallback 日志每日看，积累缺口回流阶段 3 |
| "自洽但难吃"的菜（复核口径不覆盖）            | 阶段 5 反馈闭环；无真实用户期无实际暴露面                                 |
| env2 生成质量回潮（历史停用原因）           | 生成量对齐审核消化速度；审核闭环+怪名筛+复核三道闸；批间跑覆盖率矩阵防冗余                 |
| 仿真曝光污染 dish_exposure（+~360 次） | 量小无实质影响；如在意可在仿真前快照、跑后还原                                |
| 改 sys_config 类配置的 -501007 坑   | set 数据一律不带 _id；写后回读验证（本规划期间已两次踩实）                      |

## 六、明确不动的东西（红线）

1. live 分支代码零改动（熔断兜底通道常在）
2. dish_ingredients 等分表数据结构不动（展示分组纯前端/返回体层）
3. AI 复核口径不动（清单含调料的一致性检查照旧）
4. 跨账号回写（真机验证铁律）、R-Env-01 部署验证、R-VCS git 纪律照旧执行
